MK MediKong repo split proposal 서비스와 배포 책임을 분리하기 위한 팀 제안서

서비스 개발과 인프라 운영을 같은 repo에 묶어두지 않기.

현재 구조를 한 번에 버리는 제안이 아닙니다. 앱, 배포 선언, 클라우드 인프라를 분리하고 로컬에서는 manifest repo로 하나의 작업공간처럼 다루자는 제안입니다.

Proposal

핵심 repo는 4개입니다. 하나는 작업공간을 묶는 manifest repo, 나머지 셋은 실제 작업 repo입니다.

왜 지금 분리하는가 4개 repo 구조 개발과 배포 흐름 단계적 이주안 GitHub Organization 심화 검증 목표

Problem

지금 고민은 repo 구조 문제가 아니라 책임 경계 문제입니다.

서비스 코드는 "어떻게 동작하는가"를 설명하고, 배포와 인프라는 "어디에, 얼마나, 어떤 정책으로 운영되는가"를 설명합니다. 이 둘이 계속 같은 변경 단위로 묶이면 심화 프로젝트로 갈수록 리뷰와 배포 판단이 흐려집니다.

서비스 변경과 인프라 변경의 속도가 다릅니다.

Python 서비스는 자주 바뀌지만 VPC, IAM, 클러스터, 배포 정책은 더 느리고 신중하게 바뀌어야 합니다.

리뷰 관점이 섞입니다.

API 코드 리뷰와 Terraform, Argo CD, HPA, NetworkPolicy 리뷰는 보는 사람이 달라야 할 수 있습니다.

앱 개발자가 배포 세부를 계속 의식하게 됩니다.

앱 개발자는 테스트와 이미지 빌드까지만 책임지고, 배포 반영은 GitOps 흐름이 맡는 구조가 더 좋습니다.

심화 과제가 repo 경계를 요구합니다.

독립 배포, DevSecOps, 관측성, 권한 분리, 환경별 운영 정책은 repo 구조에서도 분리되어야 설명하기 쉽습니다.

Target Structure

repo는 4개. 로컬에서는 하나의 프로젝트처럼.

GitHub상 책임은 분리하고, 로컬 개발자는 manifest repo 하나를 기준으로 전체 작업공간을 받습니다. manifest repo는 코드를 소유하지 않고 repo 목록과 bootstrap 도구만 관리합니다.

medikong-workspace

repo manifest, bootstrap, update, status 스크립트를 제공하는 진입점입니다. 팀원은 이 repo 하나로 전체 작업공간을 구성합니다.

medikong-services

서비스가 어떻게 돌아가는지를 관리합니다.

  • FastAPI 서비스 코드
  • dashboard 화면
  • pytest와 E2E 테스트
  • Docker image build
  • ECR push 또는 image publish
medikong-gitops

서비스가 어디에 어떻게 배포되는지를 관리합니다.

  • Kubernetes base와 overlays
  • Argo CD Application
  • image tag와 replica 정책
  • HPA, PDB, NetworkPolicy
  • observability와 배포 runbook
medikong-infra

클러스터와 클라우드 자원 자체를 관리합니다.

  • Terraform
  • AWS VPC, EC2/EKS, ECR, IAM
  • Ansible과 kubeadm 구성
  • 로컬 Kubernetes lab
  • 인프라 운영 문서

Operating Model

앱 repo는 이미지를 만들고, GitOps repo가 배포를 결정합니다.

Python 서비스 개발자는 브랜치, PR, 테스트, 이미지 publish까지만 신경 씁니다. 운영 환경에 반영할지, 어떤 tag를 어느 환경에 올릴지는 GitOps repo에서 추적합니다.

01 서비스 코드 변경

개발자는 medikong-services에서 브랜치를 만들고 Python 서비스 코드를 수정합니다.

->
02 테스트와 이미지 publish

CI가 pytest, E2E, image build를 실행하고 ECR 또는 registry에 immutable tag를 push합니다.

->
03 GitOps PR 생성

자동화가 medikong-gitops의 image tag 변경 PR을 만들고, 배포 변경은 별도 리뷰를 받습니다.

04 배포 선언 merge

GitOps repo의 overlay가 업데이트되면 해당 환경의 원하는 상태가 Git에 기록됩니다.

->
05 Argo CD sync

Argo CD는 앱 source repo가 아니라 medikong-gitops를 바라보고 클러스터 상태를 맞춥니다.

->
06 운영 검증

관측성, smoke test, rollback 기준이 GitOps repo의 runbook과 함께 관리됩니다.

Responsibility Split

두 질문을 repo 수준에서 분리합니다.

좋은 분리는 폴더를 나누는 것이 아니라 의사결정 위치를 나누는 것입니다. 아래 기준으로 PR 책임자, CI, 승인 기준을 다르게 가져갈 수 있습니다.

질문 관리 위치 예시
서비스가 어떻게 돌아가는가? medikong-services API, 비즈니스 로직, 테스트, Dockerfile, 의존성, health check 구현
서비스가 어디에 배포되는가? medikong-gitops local, aws-smoke, staging, prod overlay와 Argo CD Application
얼마나 배포되는가? medikong-gitops replica, HPA, resource request, PDB, rollout 정책
클러스터는 무엇으로 구성되는가? medikong-infra Terraform, AWS 네트워크, IAM, ECR, kubeadm, Ansible
팀원은 어디서 시작하는가? medikong-workspace manifest.yaml, bootstrap.sh, update.sh, status.sh

Advanced Validation

심화 프로젝트에서는 운영 지표와 테스트 시나리오까지 검증합니다.

repo 분리는 단순 정리가 아니라 검증 범위를 넓히기 위한 기반입니다. Prometheus와 Grafana로 지표를 보고, 다양한 장애와 부하 시나리오를 반복하면서 배포 정책이 실제로 안전한지 확인합니다.

관측성 지표 검증

Grafana와 Prometheus를 통해 서비스와 클러스터 상태를 수치로 확인합니다.

  • 서비스별 요청 수, 에러율, 응답 시간
  • Pod CPU, memory, restart, saturation
  • Kafka consumer lag과 이벤트 처리 지연
  • 배포 전후 지표 비교와 대시보드 증빙

테스트 시나리오 확장

단위 테스트를 넘어 실제 운영 흐름에 가까운 E2E와 smoke 시나리오를 늘립니다.

  • 환자 예약부터 알림 발송까지의 업무 흐름
  • 인증 실패, 권한 부족, rate limit 확인
  • 배포 직후 smoke test와 rollback 판단
  • 환경별 local, aws-smoke 검증 결과 기록

탄력성과 장애 실험

HPA, PDB, rollout, 장애 격리 정책이 실제 조건에서 동작하는지 확인합니다.

  • 부하 증가 시 HPA scale-out 확인
  • Pod 장애와 node 점검 중 최소 가용성 확인
  • 의존 서비스 장애 시 fallback과 부분 응답 확인
  • Canary 또는 단계적 배포의 rollback 조건 검증

보안과 정책 검증

DevSecOps와 Kubernetes 정책이 배포 전후에 실제로 차단 효과를 내는지 봅니다.

  • Trivy config/image scan과 취약 설정 차단
  • NetworkPolicy로 의도하지 않은 통신 차단
  • ServiceAccount, RBAC, secret 노출 범위 확인
  • 정책 위반 manifest의 배포 실패 증빙
services metrics endpoint, tracing hook, 테스트 코드
gitops Prometheus rule, Grafana dashboard, rollout policy
infra cluster capacity, node role, monitoring stack 기반
workspace 검증 명령과 결과 재현 절차의 진입점

Benefits

분리했을 때 얻는 것.

가장 큰 이점은 앱 개발자와 플랫폼 운영자가 같은 repo에서 서로의 발을 밟지 않게 되는 것입니다. 심화 프로젝트의 독립 배포, DevSecOps, 관측성 과제를 설명하기도 쉬워집니다.

독립 배포

한 서비스의 코드 변경이 곧바로 클러스터 설정 변경이 되지 않습니다.

  • 서비스별 release tag 관리
  • GitOps PR 기반 배포 승인
  • rollback 지점 명확화

권한 분리

앱 repo 권한과 AWS/Terraform 권한을 다르게 운영할 수 있습니다.

  • 인프라 변경 리뷰 강화
  • secret 접근 범위 축소
  • 운영 사고 반경 축소

학습 주제 강화

심화 프로젝트에서 요구하는 운영 관점을 repo 구조로도 보여줄 수 있습니다.

  • GitOps와 Argo CD
  • 환경별 overlay 전략
  • 관측성과 보안 정책

Trade-offs

분리하면 생기는 비용도 있습니다.

repo를 나누면 구조는 명확해지지만, 조합을 관리하는 비용이 새로 생깁니다. 그래서 manifest repo와 자동화된 GitOps PR이 같이 필요합니다.

여러 repo를 함께 바꿔야 할 수 있음

새 서비스 추가, 포트 변경, env var 추가는 services와 gitops를 함께 건드릴 수 있습니다.

  • 해결: 서비스 배포 계약 문서화
  • 해결: GitOps PR 자동 생성

버전 조합 관리가 필요함

어떤 서비스 image tag가 어떤 manifest와 맞는지 추적해야 합니다.

  • 해결: immutable image tag 사용
  • 해결: manifest repo에 repo 조합 기록

로컬 진입이 복잡해질 수 있음

한 repo clone으로 끝나지 않기 때문에 초기 진입점이 필요합니다.

  • 해결: medikong-workspace bootstrap 제공
  • 해결: 전체 repo status 명령 제공

E2E 검증 위치가 애매해질 수 있음

앱 테스트와 실제 배포 manifest 검증을 어떤 CI에서 묶을지 정해야 합니다.

  • 해결: services CI는 앱 검증
  • 해결: gitops CI는 manifest 렌더링과 배포 smoke 검증

Migration Plan

현재 repo는 보존하고, 옆에 새 구조를 세웁니다.

한 번에 갈아엎지 않습니다. 현재 repo는 기준점으로 두고, 새 repo들을 만든 뒤 CI, 이미지, Argo CD sync까지 검증되면 기존 repo를 legacy reference로 전환합니다.

services 먼저 분리

Python 서비스 코드, dashboard, 테스트, image build workflow를 옮깁니다.

  • pytest 유지
  • E2E 유지
  • ECR push 검증

gitops 분리

k8s manifest와 Argo CD Application을 옮기고 Argo CD의 repoURL을 전환합니다.

  • overlay 정리
  • tag update PR
  • sync smoke test

infra 분리

Terraform, Ansible, 로컬 Kubernetes lab을 운영 repo로 분리합니다.

  • 권한 정리
  • secret 제외 확인
  • bootstrap runbook

workspace 추가

repo manifest와 bootstrap 스크립트로 로컬 작업공간을 하나처럼 묶습니다.

  • clone 자동화
  • update/status 명령
  • 팀 온보딩 문서
제안의 핵심

GitHub repo는 책임별로 나누고, 로컬 경험은 manifest repo로 다시 하나처럼 묶습니다.

GitHub Organization

repo가 4개로 나뉘면 개인 계정보다 Organization이 자연스럽습니다.

이 프로젝트는 실습과 시연 목적이므로 repo를 Public으로 유지해도 괜찮습니다. 다만 GitOps와 인프라 repo는 권한, secret, branch protection을 더 엄격하게 관리해야 합니다.

추천 운영 방식

GitHub Organization 아래에 4개 repo를 모으고, 팀과 권한을 repo 성격에 맞게 나눕니다. 이렇게 하면 프로젝트가 하나의 플랫폼처럼 보이고, 심화 프로젝트의 운영 책임 분리를 더 설득력 있게 보여줄 수 있습니다.

Public workspace

manifest와 bootstrap 중심이라 공개 부담이 낮습니다.

Public services

서비스 코드와 테스트를 포트폴리오로 보여주기 좋습니다.

Public gitops

단, Secret 실값 없이 overlay와 정책만 공개합니다.

Public* infra

공개 가능하지만 tfstate, key, 계정 정보는 절대 제외합니다.

maintainers

모든 repo의 설정과 branch protection을 관리합니다.

app-developers

medikong-services에 write 권한을 갖고, GitOps repo에는 PR로 배포 요청을 남깁니다.

platform-operators

medikong-gitops와 medikong-infra의 리뷰와 merge를 담당합니다.

security defaults

secret scanning, push protection, main branch protection, 최소 Actions 권한을 기본값으로 둡니다.

For Discussion

팀에서 먼저 합의할 질문.

이 구조는 기술보다 운영 약속이 중요합니다. repo를 나누기 전에 어떤 변경을 누가 승인하고, 어떤 자동화가 어떤 repo를 수정할 수 있는지 먼저 정해야 합니다.

서비스 image tag 규칙은 무엇으로 할 것인가? commit SHA, semantic version, release tag 중 선택
GitOps repo의 환경 이름은 어떻게 둘 것인가? local, aws-smoke, staging, prod 등
앱 repo CI가 GitOps repo PR을 자동 생성해도 되는가?
인프라 repo의 Terraform apply 권한은 누가 가질 것인가?
기존 cloudnative_study repo는 언제 archive 또는 legacy reference로 바꿀 것인가?
